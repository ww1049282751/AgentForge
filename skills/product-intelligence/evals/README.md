# 产品研究行为场景

场景定义和原始输入供按需试跑使用，不代表已经执行或通过。所有 fixtures 以及复用的 examples/source-material.md 都是明确标注的合成材料；不能计入真实用户样本。

## 执行方式

1. 从 scenarios.json 选择与此次改动相关的场景。inputFiles 路径相对于本目录；文件必须存在于当前技能内。
2. 给执行者技能入口、该场景的 request，以及 inputFiles 指向的原始材料。不要提供整个 scenarios.json、expected、评分规则或分析正反例。已有技能资源可能被执行者主动读取，应记录这项限制，不据此宣称独立或盲测。
3. 如果场景有 followup，先保存第一轮输出，再发送 followup。需要检查触发的负例，不强制加载技能正文；记录实际环境是否能观察触发，不能从回答形式反推自动触发成功。
4. 完成后再由审查者读取 expected 与 [评分依据](rubric.md)，结合原始输出记录观察与理由。测试用户研究能力不等于进行真实访谈；所有结果都保留合成/离线边界。
5. 输出、工具行为及用户反馈保存在用户授权的本地位置；在作者仓库内使用 .local/skill-evals/，可提交的仅为脱敏结果。记录实际读取的技能内容散列、模型与工具条件、输出和观察理由；无法取得的信息明确记为未知。同题对照需要相互隔离的上下文，不让执行者看到另一组结果。

## 本轮补齐

- 将代码修复、UI 小改与短句翻译拆成独立负例。
- 给离线、过期资料、薄弱证据、材料注入与私密信息场景补上可读取的原始输入。
- 新增功能请求与用户任务、竞品未说明的能力、竞争性解释、机制迁移条件、限定范围的小问题和研究收束场景。
- 观察标准强调证据范围、替代解释、机制差异、反证与有条件建议，不要求固定方向数量、固定措辞或预设最终方案。
- 增加备课领域的混合记录场景，检查当前探索请求是否被材料里的局部交付选择带偏；与原研究场景一起检验范围对齐，避免只记住一种表格/页面案例。

结构检查只验证场景字段与输入路径；单元测试只验证检查代码及样例证据映射。它们都不是模型行为验收。
