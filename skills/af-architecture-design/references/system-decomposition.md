# 系统分解与关键机制

用于 design 的落地部分、deep-design 与模块重划。按实际风险细化，不强制 DDD 术语或统一层数。

## 边界与所有权

从业务动作和不变量划分职责。每个关键模块说明输入、输出、拥有的数据与允许调用；模块边界不必等于进程边界。说明谁能修改哪类数据，跨模块查询通过什么契约，事务为什么在此提交。共享数据库不等于所有模块可任意跨表写入。

沿关键路径检查依赖方向及循环：调用方依赖稳定接口，技术适配由实现承接；不要只按 controller/service/repository 名称声称隔离成功。必要时给“模块 → 允许依赖 → 数据拥有者”小表，列跨边界写入与禁止依赖的检查方式。

## 接口与状态

对关键命令或事件写清身份/租户上下文、必要字段、标识符、前置状态、响应或错误、超时语义、兼容方式。不必定义全部 OpenAPI，但后续实现者应知道重放同一请求、同键不同载荷、无权限和竞争修改时发生什么。

状态转换指出触发者、合法前态、原子更新条件和终态。超时通常只表明调用方未获知结果；需要查询、对账或同一操作标识重试，不能直接等同失败。回调乱序、重复和迟到要结合当前状态与操作标识判断，不可用旧结果回退已确认状态。

## 可靠性推演

围绕一个具体不变量，逐个把进程中断放在“提交前、提交后、发送前后、收到响应前、确认消息前”观察结果：

| 风险 | 需要具体决定 |
| --- | --- |
| 并发/重复请求 | 业务操作键的范围和保留期，同键载荷校验，唯一约束或条件写；去重记录与业务变化的原子边界 |
| 本地状态与消息双写 | 是否能同事务存业务变化和待投递记录；投递器如何重试、观测积压、恢复和清理 |
| 消费重复 | 处理结果与去重标记是否同一事务；提交成功后再确认；不能先标完成再执行业务 |
| 外部不可原子副作用 | 供应方幂等键/查询能力、持久化操作意图、结果未知状态与对账；能力不足时人工处置，不能承诺严格一次 |
| 并发状态更新 | 唯一约束、条件更新、锁或适用隔离级别如何保护不变量；事务重试范围与冲突错误语义 |
| 持续失败 | 超时预算、有限重试及退避、不可重试错误、隔离失败记录、告警和人工恢复路径 |

事务 outbox 解决本地提交与事件记录的双写窗口，不消除重复投递，也不替第三方调用提供原子提交。若无需异步解耦，先比较同进程事务或数据库任务表，避免为了使用模式引入队列。[AWS outbox 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 支持这一机制与重复消费边界；采用具体产品时仍核实当前配置和能力。

数据库隔离级别不能仅凭名称推断全部行为。例如 [PostgreSQL 事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html) 要求应用处理序列化失败；使用此机制时重试整个事务，并避免在可回滚事务内直接重复不可回滚的外部副作用。此例不是要求所有项目换数据库。

最终交付一个正常路径和任务相关的异常路径，连到可以复现的检查；未知保留为未知，不用图替代契约。
