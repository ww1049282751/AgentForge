# 架构评审、验证与演进

用于 review、validation、evolution。方法依当前工具和权限选择；不把本文件当作执行生产变更的授权。

## 审查已有方案

先限定对象、版本和证据范围。文档明确规定的“提交后再发消息且不补偿”可判为设计中的丢失窗口；未看代码和运行记录则不能断言线上已经丢失。缺少某段设计可能意味着文档不全，不必直接判为实现缺陷。每项重要发现包含：

- 问题与精确位置，属于明确缺陷、条件成立的设计风险或待验证假设。
- 成立条件、影响对象与优先级理由，避免用个人栈偏好定级。
- 最小修正及有竞争力的替代，新增代价。
- 可判定是否修复的检查/测试；仍需哪项源码或观测证据。

优先处理会破坏核心不变量、授权隔离或恢复路径的问题。没有证据的泛化建议单列，不用问题数量代表审查深度。

## 验证任务

从关键决策倒推最小验证：假设、输入/前置状态、操作或故障点、可观察结果、验收判据、执行环境、实际状态与证据位置。阈值未定时仍可检验正确性不变量；性能验收标待确认，不能自行设数字后宣称达标。

区分以下证据：设计推演只解释风险；静态依赖/契约检查验证指定源码规则；原型只支持原型环境；测试报告需命令、版本、条件和实际输出；生产观测只支持观察时段与流量。历史报告标日期，不改称本轮重跑。

适用检查包括循环依赖、跨模块写入、接口兼容、状态机非法迁移、并发冲突、重复请求/消息、提交与确认之间崩溃、超时后迟到成功、备份恢复及迁移演练。按项目现有测试命令执行；没有可执行系统就交付测试任务和待验证状态，不伪造测试用例已经运行。

## 渐进演进

1. 列现状、目标与差异：调用方、数据拥有者、写入路径、接口和存量数据。保留不能变的契约及当前已知缺陷。
2. 先建立兼容边界：新增字段或接口、适配旧调用方、依赖观测，避免先删旧能力。分阶段替换可参考 [Strangler Fig 模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)，但路由层也是新增故障点，小系统未必需要它。
3. 定义每阶段唯一权威写入方。复制/回填说明快照边界、变更捕获、顺序、幂等、删除和校验；不要把无协调双写当默认迁移方案。
4. 切换前验证完整性、增量追平及调用兼容；必要时短暂限制写入或建立写入栅栏。分批切换的单位要明确，避免同一业务对象两边同时接受冲突写入。影子读取需避免执行副作用。
5. 每阶段说明进入/退出条件、观测信号、暂停条件、操作顺序与回滚前提。阈值未知就标待协商。新系统接受写入后，旧数据可能落后：需反向同步/对账、前向修复或停写处理，不能只回滚路由和代码。
6. 旧接口/字段/组件仅在调用方已迁移、数据验证与恢复窗口结束后退役。破坏性清理与实际生产操作另按任务授权执行，不在设计中保证零停机或无损。

用一次演练检验切换中断、迁移重复执行、回填期间写入及回滚后的读写一致性。输出的计划本身不构成演练通过。
