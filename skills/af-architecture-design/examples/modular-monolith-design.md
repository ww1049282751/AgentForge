# 合成示范：内部器材借用

本页是作者编写的合成设计示例，不是模型行为试跑、真实用户项目或测试通过证据。数字仅是本例虚构输入，不应沿用到其他任务。

## 输入与选择

假设输入：一个办公室、40 名员工、两名开发者，现有单应用部署和关系数据库；需要申请借用、管理员批准、归还和审计，不要求对接外部系统。负载、延迟目标和恢复目标未提供。

推荐在现有应用内划清器材目录、借用和身份/审计职责。最强替代是更简单的单模块 CRUD；如果不用审批且没有并发竞争，单模块可能已经够用。本例增加借用状态和占用不变量，单独隔离借用逻辑便于检验，尚无独立部署收益支撑微服务和消息平台。

代价是共享部署及数据库资源，模块边界需依赖规则维护；收益是本地事务可保护借用与器材占用一致。若未来跨团队独立发布或长任务显著干扰在线请求，先测影响再考虑进程隔离，不预设拆分时间。

## 关键实现模型（拟议）

目录模块维护器材资料；借用模块拥有申请与占用记录；身份适配验证员工身份，借用模块执行对象与角色权限。目录不反向调用借用，任何占用修改经借用接口。审计记录与状态变化同本地事务提交，日志不含敏感凭据。

`POST /loans` 输入器材标识和操作键，申请人从身份上下文获取；返回申请标识与 pending 状态。键按申请人作用域唯一，同键同载荷返回原结果，同键不同载荷报冲突。`POST /loans/{id}/approve` 同样接收操作键：验证当前管理员及对象权限后，先查该管理员、批准动作与操作键的原结果，校验申请标识和载荷；已完成的同键请求重放原响应，不再次要求 pending，同键不同载荷报冲突。首次批准才校验 pending 前态，在一事务内记录占用、改 approved、保存该键对应的结果；唯一键或条件写协调同键并发，业务竞争失败返回冲突，不先查后写。另用数据库可支持的唯一活动占用约束或条件写保护“一件器材最多一个活动借用”。`POST /loans/{id}/return` 校验对象权限，释放占用并转 returned；重复归还返回已有结果，不新建审计动作。

合法主链 pending → approved → returned；pending 可 rejected，非法跳转拒绝。客户端超时不表示事务失败：用原操作键重试或查询申请。无外部通知需求，不额外部署异步系统。

## 验证计划（均未执行）

| 场景 | 判据与方法 |
| --- | --- |
| 两个管理员同时批准同一器材的不同申请 | 同步并发请求，最多一个活动占用；失败申请保持一致状态 |
| 批准事务提交前中断/提交后丢响应 | 前者占用、状态和操作结果均无部分提交；后者同键同载荷重试返回原批准结果，没有第二次占用；同键不同载荷报冲突 |
| 非管理员批准、访问他人申请、重复归还 | 越权拒绝且无数据变化；允许的重复归还不重复副作用 |
| 备份恢复 | 在测试环境恢复并核对申请、占用与审计不变量；恢复目标待确认 |
| 性能 | 先收集典型负载与响应目标，再测热点审批；现在不声明吞吐或延迟达标 |

实施先定义状态和约束，再完成身份及接口，随后验证并发、恢复和权限。此例仍缺真实部署容量与恢复演练，不能从设计正确性推导生产表现。
