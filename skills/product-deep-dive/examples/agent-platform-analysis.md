# 合成示范：Agent 任务重启后发生了什么

本例为作者编写的合成方法示范；对象、观察和引用编号均为虚构材料，不是模型试跑、真实源码研究、市场证据或测试结果。它不描述 evals 的输入项目。

## 合成原始片段

- S1，虚构产品“纸桥”的说明页：“任务中断后可以继续执行。”版本和生产配置未给出。
- S2，虚构实现片段：入口 `submit()` 写入任务；`worker()` 领取后执行工具，再保存 `step_result`；`recover()` 找出未完成任务并重跑当前步骤。未提供工具服务或部署配置。
- S3，虚构演示记录：进程重启后仍显示相同任务 ID，最终出现结果。没有逐步日志。

## 研究解释

核心用户任务是提交工作并取得结果；任务、步骤、工具结果是不同对象。当前机制模型为“持久任务 → 领取步骤 → 工具副作用 → 保存结果 → 输出”。它解释了恢复入口，但“副作用后、保存前”的空窗尚未闭合。

| 主张 | 依据与类型 | 范围 |
| --- | --- | --- |
| 产品宣称支持中断继续 | S1，E3 | 仅为合成来源的承诺，不能证明恢复方式 |
| 实现片段在恢复时重跑步骤 | S2，E2 | 仅证明片段内逻辑；未证入口可达、测试或生产启用 |
| 恢复可能重复外部副作用 | S2，E4 | 若工具端没有去重；也可能由未提供的下游幂等处理消除 |
| 相同任务 ID 不足以区分续跑与重算 | S3，E4 | 演示缺少步骤日志；并非研究者的 E1 |

下一项高价值证据是工具请求的幂等键与结果提交边界；之后可设计“工具成功但保存前中断”的实验。本文没有执行实验，不能写作测试通过或发现真实漏洞。

## 候选模式与停止

候选模式是“把恢复身份延伸到副作用边界”：重试沿用稳定操作 ID，由接收方去重或提供结果查询。潜在收益是减少重复处理；代价是去重存储、过期策略和跨系统契约。它适用于下游支持幂等或查询的场景；非幂等服务可能需要人工确认或补偿，不能宣称恰好一次。

这是从合成片段推导的候选，不是已验证跨产品规律。当前只能解释任务持久化不等于副作用恢复保证；真实实现与运行配置不可得，继续增加宣传资料不会回答此分歧，因此在明确验证路径后停止。
