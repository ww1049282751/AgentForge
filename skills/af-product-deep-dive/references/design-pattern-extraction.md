# 从产品机制提取候选模式

在机制已解释且对本次研究有价值时使用。模式是待检验的知识抽象，不是每份报告的必填章节，也不是用户项目的自动开发计划。

## 抽象与比较

1. 回到来源产品的具体问题和证据：什么状态、约束或失败促成这种做法？设计动机有作者陈述就引用，没有则标为推断。
2. 去掉品牌和技术名称后，描述机制及必要不变量；保留它与相似实现的关键差异。只有功能相似不能证明采用同一实现或具有相同效果。
3. 与至少一个有实质差异且与任务相关的替代比较收益、代价和成立条件；替代若未调研则作为理论选项，不能捏造另一产品实现。
4. 给出不适用场景、失败模式、反例和能推翻迁移判断的证据。单产品发现可形成候选模式，不自动成为跨产品规律；多来源也需检查是否只是互相转述。

使用 [模式记录](../templates/design-pattern.md) 或简短文字保留来源、问题、机制、条件、成本、未知。用户需要迁移时再连接其约束：迁移哪一部分、需怎样改造、哪些前提不成立及怎样验证。不把知名产品采用过当成值得照搬的依据。

## 保存与更新

默认在当前会话交付。用户授权归档后，先查已有研究/模式，选择补充原条目或新建，记录来源版本、研究日期、支持与反驳、候选/已核查范围和修订原因。

可以按产品保存概览、架构、证据和开放问题，但仅创建本次需要的文件。保留争议解释和历史依据，不自动覆盖其他项目或写全局知识库，不创建后台更新任务。资料新增只在确实改变机制理解时更新结论，重复来源不算新增独立证据。
