# 设计与编写

用于 CREATE、职责重划或资源组织有问题的任务。局部措辞修正不必重新设计整个技能。

## 是否值得固化

从用户最近的任务或明确反馈提取：反复出现的决策、普通执行容易遗漏的信息、可复用的方法和可观察的完成条件。频繁出现本身不够：若只是已有工具的一步操作，短提示可能更合适；一次复杂任务也可能沉淀可复用方法，说明预期重复场景而非伪造历史频率。

查目标仓库已有技能与资料，比较实际任务覆盖而非名称相似度。若现有技能已经覆盖，直接给出使用入口；若仅缺一个分支，优先局部扩展；若职责不同且能独立输入、交付、评估，再考虑新技能。合并会影响现有调用时先提出影响和迁移方案，不自行删除旧入口。

至少写清“缺口是什么、最简单替代是什么、为什么值得或不值得新建”。不要求打分、固定门槛或额外审批。明确而充分的创建任务可直接推进；只有缺少会改变范围的事实才询问。

## Skill Spec 的设计作用

使用 [规格模板](../templates/skill-spec.md) 把需求变成可执行约束。Goal 与 Outputs 应可观察；Scope 与 Trigger 要能区分相邻任务；Workflow 写影响结果的判断与停止条件，不重复常识。Resources 每项对应一个具体用途，并说明何时加载。Evaluation 写能暴露错误的任务和失败信号，而非只要求生成几个文件。

Maintenance 绑定已观察变化：用户反馈、重复失败、接口或规范变化、资源失效。缺少输入时标记未知与取得方式，不用推测补成既定要求。Spec 可以只存在于会话，不引入配置注册表、JSON 协议或运行时。

## 最小完整实现

从 `SKILL.md` 开始。入口足够短且自包含时无需 references；有实际输出复用才加 templates；展示难以理解的取舍才加 examples，标明合成内容；只有确定性重复操作才写 scripts，并交代依赖、输入和副作用。不要创建空目录或待办占位文件。

frontmatter 简介回答“何时用它”，不要为了关键词覆盖吸收不相关请求。正文给模型决策空间：开放任务采用目标和判断标准；有真实风险的操作写必要顺序和停止条件。不要把某次失败的局部修补变成全部任务的必经流程。

新资源链接相对当前文档，目标保持在技能目录内。仓库维护文档可以指向技能，技能不依赖作者仓库的 docs 或其他技能的相对路径。完整复制文件夹后核对入口、链接和原始输入清单。

## 与其他工作的边界

产品探索、源码研究和普通开发由对应能力完成；这里只在用户要求沉淀或改进技能时利用其成果。内容可以借鉴其取证、反证和渐进加载原则，不复制领域专属模板为通用规范。

目标目录已存在时读取、比较后再决定修改，保留独立用户内容；只要方案时连临时脚手架也不自动落盘。创建工作文件不意味允许安装到用户目录或远端发布。涉及迁移时先建立可核验快照，再更新当前引用；历史名称、研究结果与旧版本保留其当时含义。
