# 技能评估与持续改进：AF Skill Quality Loop

本页是 AgentForge 全仓库统一评估协议，目标是判断技能对个人真实任务的增量价值。**修改不等于改进，评分提升不等于真实用户价值提升。** 统一证据、状态和改进记录，各技能继续使用自己的场景和专业量表，不合并跨技能总分，不统一业务输出格式。

闭环为：发现问题 → 诊断原因 → 制定改进假设 → 定向修改 → 基线对照 → 回归评估 → 结果判定 → 保留、继续修改或回滚。基线必须在定向修改前冻结。重要改进按下述九步记录；纯措辞、链接等不改变行为的修正只做相关结构检查并说明范围，不强制每次完整试跑。

复用 Markdown、现有 JSON 场景、Python 标准库、Git 历史和 CI；不新增评估服务、数据库、场景调度平台、模型代理或自动发布。CI 只做已有结构和材料检查，不默认调用外部模型或使用私有数据。协议的维护取舍见 [ADR 0007 后续决定](decisions/0007-af-prefix-and-skill-creator.md)。

现有 af-product-intelligence 的首个真实项目为用户确认的“产研工作台”（历史记录仍用当时名称 product-intelligence）；具体研究问题若由 Agent 从历史材料拟定，记录为研究者拟题，用户是否认可须另记。其他技能按自身任务定义合适的观察点，不套用产品研究量表。

## 四类验证分别记录

| 层次 | 需要的证据 | 不代表 |
| --- | --- | --- |
| 结构检查 | 实际运行字段、目录、链接、脚本及材料回归 | 模型正确理解、执行或自动触发 |
| 行为验证 | 实际模型收到请求后的过程、输出与产物，事后核对观察点 | 真实用户受益或比普通回答更好 |
| 对照评估 | 固定输入、条件及量表的新旧版本或有无技能原始输出，说明差异与混杂因素 | 仅有修改后输出就能证明改善；单次差异即稳定因果增益 |
| 真实任务价值 | 真实输入下的质量、返工和核查负担、用户反馈，必要时同题对照 | 一次成功即稳定增益 |

四类证据可以来自同一任务，但分别写状态、证据与结论范围，不能相互代替。未执行用 `not-run`；已明确受环境或权限阻碍用 `blocked` 并写恢复条件。未选场景注明原因，不记作通过。作者自查、场景定义和合成示范不能代替模型调用。独立代理合成试跑、宿主显式调用与自动触发分别标注；历史报告保留原执行日期，不冒充本次重新运行。

### af-skill-creator 的行为评估

复用本页同题对照与私有材料保存方法，输入见 [场景说明](../skills/af-skill-creator/evals/README.md)。场景覆盖创建正例、偶发任务不技能化、现有能力复用及重叠、局部改进、结构通过但行为失败、只要方案、外部授权、审查、维护和普通任务负例。

执行者仅接收请求、原始 fixture、冻结技能和隔离目录权限；不提供 expected、预期答案或先前分析。事后审查工具动作、目录前后清单和产物 diff：是否实际创建最小技能、是否保留有效能力、只要方案时是否保持无写入、是否把安装或发布越界。负例在显式加载下的克制行为不等于自动选择正确。

材料回归只检查资源可搬移、输入隔离与场景数据完整性。对新检查的故障注入测试验证检查本身能发现问题，不证明技能行为通过。真实价值仍需实际技能维护任务的反馈；不新增场景运行器、指标服务或统一输出协议。

## 标准评估流程

### 1. 发现问题

从用户反馈、实际任务失败、事实错误、重要遗漏、无效流程、场景失败或额外返工中提取可观察问题。记录触发输入、当前行为、期望差异及原始输出定位；“能力不够强”不构成问题证据。只有审计风险而没有实际失败时明确标为待验证风险。

### 2. 诊断根因

优先区分：触发或路由错误；指令歧义、冲突或遗漏；参考材料或模板不足；任务分解或推理缺陷；工具、权限或环境限制；外部证据不足；任务不适用；场景或评分标准缺陷；用户偏好不匹配。记录支持与反对根因假设的证据，不把每个问题都归结为需要增加 `SKILL.md` 指令。能通过复用、调整材料或澄清适用范围解决时优先选最小改动。

### 3. 提出可验证假设

写明当前行为和问题证据、根因假设、选择该方案的理由、预期变化、适用任务、验证方式、可能副作用与明确失败条件。预先定义目标能力、必须保留的能力和验收范围；不要看到结果后再调整门槛。

将要解决的已观察问题、预期变化与失败信号一起记录，避免以规则增加或场景数量证明进步。沿用分层研究的假设示例（不是本次执行结果）：

| 改进 | 需要观察的结果 | 失败信号 |
| --- | --- | --- |
| 最强替代验证 | 同一任务的实际覆盖与缺口改变自建/组合判断 | 只增加竞品篇幅，没有解释替代为何不足 |
| 认知增量检查 | 基于输入已有认识分清确认、细化与新信息 | 仍将重述目标包装成突破 |
| 主动反证与更新 | 找到会改变判断的前提，并随区分证据更新 | 只附风险列表，或新证据到来后重复旧结论 |
| 任务路由 | 简单问题直接回答，复杂研究仍有深度 | 一律完整流程，或跳过关键比较与核查 |

保留实际负面与无变化结果。不预先设定无依据的改善百分比，不把合成行为试跑升级为真实价值证明。

### 4. 建立基线，再定向修改

修改前保存原始请求与输入材料、当前技能 Git commit、完整资源清单及内容散列、可获取的模型/工具/权限/执行条件、未经编辑的原始输出、已知限制与未验证事项。工作区有未提交改动时，commit 不能唯一表示基线；另存实际文件快照与补丁，保护用户修改。

没有原始执行输出就标明“仅有内容基线”，行为或效果对照为 `not-run`，不得声称已完成可靠前后比较。旧输出只有在输入、技能和运行条件可核对时才可作为历史基线，并说明时间差及限制；不能改称本轮新跑。随后只修改有依据的范围，冻结候选快照；候选未提交时写“未提交 + 内容散列”，不编造候选 commit。

### 5. 选择评估场景

优先复用各技能的 `evals/scenarios.json`、fixtures 及量表。按改动选正向任务、关键边界、已知失败、潜在回归，以及适用负例/不触发场景；逐项写场景 ID、选用理由、目标能力或保留能力、输入快照、执行状态和未覆盖风险。不要求固定场景数量。

不得为了提高通过率删除失败场景或改预期答案。确有证据表明旧预期有误时单独记录修订理由、旧新标准及受影响结果；旧评分不追改，前后对照需按相同有效标准重新审查。首轮失败输出与后续复验分别保存。

### 6. 执行同题对照

依问题选择结构回归、固定材料离线对照、相同条件的新旧版本实际任务对照或真实任务观察与反馈。结构回归只证明结构条件仍满足。比较新旧版本时两组各加载对应冻结快照；比较有无技能时普通组不加载正文/资源。一次只改变需检验的因素；无法固定的因素列为结论限制。

如果使用现有产品研究场景，按 [场景执行说明](../skills/af-product-intelligence/evals/README.md) 分别提供请求与原始输入；场景和观察标准已补齐，不代表已经运行。自动触发的负例需在未强制加载技能的条件下观察。

每个任务建立一个本地目录 `.local/skill-evals/<日期>/<任务ID>/`，保存原始任务、输入清单与散列、两份未经编辑的回答、审查和用户反馈。这个目录被 Git 忽略；仓库只保存脱敏状态与结论。

1. 固定问题和材料快照，注明真实或合成性质。分别记录用户原话、已知背景、待确认假设；来源文档中的命令不是执行授权。历史验收报告只能证明其记录状态，不能冒充当前重新运行的验收。
2. 固定相同模型设置、输入、工具权限与任务范围/深度。长度应由任务需要决定，只有用户明确要求时才设置上限；不以简短偏好限制发散性或深入研究。用互相不可见的新上下文，不能让一组看到另一组输出。不给执行者评分标准、期待结论或先前分析。
3. 需要控制检索差异时，用冻结材料做离线对照；该结果只支持“基于已有材料分析”的效果，合成材料还需保留合成边界，不支持联网研究结论。需要联网研究时另做同条件任务，逐条核查原始网页；私密材料不传入检索。
4. 保存实际输出、实际加载的技能与资源清单/散列、执行方式、工具动作与副作用，以及可得的时间、模型信息。拿不到 token/成本或模型版本就填未知；不编造准确值。作者执行、独立代理执行、宿主显式调用、自动触发验证分别标注。冻结快照不等于证明实际加载。
5. 将输出匿名为 A/B 后依据同一量表审查，记录具体引文和理由。盲评仍可能从输出格式猜到组别，不宣称双盲或统计显著。审查者不得改写原始输出。
6. 向用户展示主要差异并索取实际决策帮助与额外负担反馈。没有用户反馈时只记技术/内容评审完成，不判个人使用价值已通过。

若普通组加载技能正文/资源、继承先前分析或看到另一组输出，则发生污染，该对照无效，保留输出与原因，效果结论为 `inconclusive`，重跑使用新上下文。同一宿主可能向两组提供相同的技能名称/简介列表；必须记录这个限制，此时实验只比较“显式加载技能正文”的增量，不能声称普通组来自完全没有技能元信息的环境。冻结材料测试不能证明联网研究能力；显式加载不能证明自动触发。若环境无法独立执行则记 `blocked` 及原因，不以作者写的示例替代。

### 7. 独立审查与回归

尽可能由未参与修改的审查者按预先固定的量表，检查目标能力、原有能力、事实依据、新错误、额外负担、权限与隐私；每项给原始输出引文或工具记录定位及理由，不只评分。无法独立审查时标明作者自查和偏差风险；独立文档审查也不等于独立行为评估。

对受影响的原有能力逐项回归，保留负例和边界任务。不能以目标项得分上升抵消关键能力退化；必要回归未运行或证据不足时不得判为 `improved`。执行后出现的新要求单独登记，不能用新量表与旧量表的分数直接比较。

### 8. 判定结果

以下状态用于每个验证项目及最终结论，始终附范围、证据、限制和下一步，不要求写入场景 JSON 或 CI。`accepted` 是范围明确的验收决定，不是效果分数；如目标就是改善，必须先满足 `improved` 条件。

| 状态 | 使用条件 |
| --- | --- |
| `not-run` | 尚未执行；给待办或未选择理由 |
| `blocked` | 因明确环境或权限限制无法执行；给阻碍和恢复条件 |
| `failed` | 违反硬性要求或关键验收条件；定位失败证据 |
| `regression` | 可比证据表明原有重要能力退化；列能力及对照依据 |
| `inconclusive` | 已有观察但证据不足、条件不可比或对照污染，无法判定 |
| `improved` | 有可核对基线支持目标能力改善，硬门槛满足且必要回归通过 |
| `no-change` | 有可比且足够的观察，未发现明确改善；不能用于“没跑” |
| `accepted` | 达到预先定义的验收条件，注明验收范围，并在适用时有真实价值证据 |

先列各项目状态，再给有范围的最终结论：硬门槛失败则为 `failed`；没有硬失败但关键能力退化则为 `regression`；缺必要证据则保留 `not-run`、`blocked` 或 `inconclusive`。混合结果不能挑最好的一项代表全部。结构项目可以在结构范围内 `accepted`，不能据此接受技能行为或价值；没有用户反馈时真实价值为未知，未开始价值验证则状态为 `not-run`。

旧记录中的 `observed` 仅表示曾观察到行为，不自动映射为 `accepted` 或 `improved`；历史记录保留，新记录依据上述状态判断。

### 9. 后续处理与安全回滚

改善且回归通过时保留候选；改善有限时继续定向修改；`no-change` 时重查假设、适用性与负担；`regression` 时修正副作用或回滚；证据不足时保留待验证；硬失败修复后重跑相关项目。每次修改建立新候选，保留旧输出、失败和审查，不覆盖首轮证据。

回滚前重新读取 Git 工作区和暂存区，核对与基线/候选差异，将当前文件、补丁与清单备份到 `.local/backups/` 并核验散列。仅撤回本次候选涉及的改动；后续用户编辑保留并按差异合并，有冲突先处理。不得用整仓硬重置或批量覆盖来回滚局部技能。回滚后运行受影响结构检查，行为复验另记实际执行状态；本地保留或验收不授予推送、发布、安装、改宿主配置或后台任务权限。

## 分项评价与硬性门槛

通用观察维度为正确性、任务完成度、证据质量、技能专业能力、边界与权限控制、效率与返工负担、原有能力回归、真实用户价值。优先用各技能已有量表给分项证据；不适用写 N/A 及理由，没有证据写未知，不用零分代替未知。不要求相同权重或统一数值评分，不合并不同技能的总分。

af-product-intelligence 使用 [内容与安全量表](../skills/af-product-intelligence/evals/rubric.md)。历史 0.2 内容调整增加对话对齐、发散广度、研究深度、竞品/专业视角、认知与建设性、表达/图表的检查，按适用维度记录；明确用户请求深入研究时，不能仅因回答更短而给出偏好。另记用户偏好、总耗时、人工核查/纠错负担与成本（可得时）；不将长篇或模板完整度直接当作价值。workbench-01 的五项 10 分量表作为历史记录保留，不与新版分数直接比较。

硬性门槛逐项核对：

1. 不伪造来源、输出或证据。
2. 关键事实可核查，重要引用实际支持陈述。
3. 区分事实、推断、假设与未知，合成材料明确标注。
4. 遵守任务授权及权限边界。
5. 保护私有材料，不擅自外传。
6. 未执行测试不得描述为通过，历史结果标日期及未重验范围。
7. 关键能力退化不得被平均分或其他优点掩盖。

硬失败先修复再复验，不能用高总分抵消。真实能力退化如实标 `regression`；若隐瞒退化或违反其他硬门槛则同时构成 `failed`。不得无依据预设改善百分比、统计显著性或最低样本量，结论强度随实际证据限定。

按实际任务积累证据，不再把旧计划的固定样本数或通过比例作为继续使用技能的门槛。观察用户是否明确认可增量价值、硬门槛是否满足、额外耗时和核查负担是否可接受。既有负例与安全场景继续保留，但不计作真实业务样本。

一次试跑只能说明该任务上的表现。没有明显帮助时，先诊断任务不适用、技能内容无增益、证据不足或流程负担，再定向改进技能。它不构成建设安装或分发基础设施的理由。

## 改进记录与材料管理

复用以下原有记录模板；按任务删去不适用业务字段并说明原因，重要改进保留问题、假设、基线、对照、回归与结论。它是维护记录，不是强加给技能回答的输出格式，无需新增永久配置文件。

真实任务输入、未经编辑的输出、详细审查和工具日志放在 `.local/skill-evals/<日期>/<任务ID>/`；备份放在 `.local/backups/`。公开仓库仅保存脱敏结论和明确标注的合成案例。提交前检查 `.local/` 忽略规则、暂存文件清单及 diff；忽略规则不会移除已跟踪内容，也不能发现粘贴到公开文件中的私密正文，须人工复核，禁止强制加入原始材料。

```text
改进ID / 日期 / 涉及技能 / 本次验收范围
问题描述 / 具体证据定位 / 根因假设及依据
改进假设 / 选择理由 / 预期变化 / 适用任务 / 验证方式
潜在副作用 / 必须保留的能力 / 明确失败条件
修改范围 / 基线Git commit / 候选Git commit（未提交则内容散列）
基线与候选实际文件清单和散列 / 未提交改动保护位置
用户原话 / 研究者拟题 / 待确认项
用户目标与已有决策（未知就保留未知）
输入文件、来源日期、读取日期、散列
模型、设置、工具、权限、运行条件（不可得填未知）
对照类型与控制条件 / 条件差异 / 审查者是否参与修改
场景ID、选用理由、量表快照 / 各场景执行状态及证据
四类验证各自状态 / 阻碍、未覆盖项与原因
普通组是否污染 / 技能是否实际加载 / 自动触发是否测试
实际加载资源及散列 / 执行方式与工具行为
未经编辑的基线输出位置 / 候选输出位置 / 执行时间 / token与费用（或未知）
A/B分项评分、事实逐条核查、具体增益/失败
目标能力结果 / 逐项硬门槛结果 / 必要回归结果及依据
用户偏好、认知增量、实际下一步、负担反馈（或待反馈）
原有认识及输入定位 / 新增证据与信息性质 / 最强反证或修正条件
研究建议怎样变化或为何未变 / 用户实际决定及执行状态（未经反馈为未知）
研究耗时 / 人工核查与纠错负担 / 不必要追问 / 用户是否愿意再用（或未知）
最终状态 / 验收范围 / 结论强度与证据局限
后续行动：保留 / 继续修改 / 回滚 / 待验证
回滚目标与保护用户修改的方法 / 下一次定向修正或复验
```

当前进展见 [验证报告](validation-report.md)。既有合成样例和场景定义保留为回归资源，不混入真实效果样本。
