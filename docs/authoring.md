# 技能编写与维护

在 `skills/<name>/` 中维护一个可独立使用的技能。必需文件只有 `SKILL.md`，其余资源按任务需要增加。

## 入口与资源

frontmatter 至少包含 `name` 与 `description`，两项使用非空单行文本。所有新技能的 name 和目录名必须完全一致、以 `af-` 开头且不重名；使用小写字母、数字和短横线，整体不超过 64 字符，短横线之间不得为空。description 说明技能的实际能力和适用任务；只有在容易误触发时才补充排除范围。现有迁移映射与边界见 [ADR 0007](decisions/0007-af-prefix-and-skill-creator.md)。

主入口保留目的、关键行为、边界以及相关资源链接。详细方法放入 references，输出模板放入 templates，示例放入 examples，行为场景和评分依据放入 evals。可选脚本仅在解决具体重复任务时增加，说明自己的使用方法及依赖；不为集合建立统一运行时。

既有 af-product-intelligence 的分析正反例属于方法说明，保留在 references 中；完整合成研究演示放在 examples 中。位置服从实际用途，不要求每种材料机械归类。

分层以职责为界：入口决定任务、深度、资源和停止条件；参考文档维护详细方法；模板帮助交付与核查。每项参考资源应说明何时读取，避免入口和模块复制整套步骤。af-product-intelligence 的具体取舍见 [ADR 0005](decisions/0005-layered-product-research.md)。其他技能可复用渐进加载、证据边界和失败记录原则，不套用产品研究流程或强制三层目录。

## 维护过程

### 能力应放在哪里

先识别缺口的性质，再选最简单的载体；同一需求可拆成几种资产，不要求新建目录或统一登记表。

| 类型 | 判断与首选载体 | 例子 |
| --- | --- | --- |
| Skill | 可重复的专业判断，有独立任务、触发与验收；先复用现有技能 | 约束下的架构权衡 |
| Policy | 长期通用约束、授权边界，写入适用的 AGENTS.md | 保护未提交修改 |
| Knowledge | 有来源、版本和适用范围的经验，放对应 references 或项目文档 | 幂等失效案例 |
| Tool | 确定性、可复现操作，复用工具或小脚本 | 计算内容散列 |
| Context | 当前目标、版本、决策与未完成状态，留在项目记录或按需交接中 | 当前分支与待确认事项 |
| Evaluation | 验收与比较材料，复用 evals 和统一质量协议 | 正负例、基线与回归 |

选择独立技能前，应能说明可验证缺口、方法是否稳定、与相邻任务的边界、独立验收方式，以及相比普通 Agent、已有技能、一次性提示、参考资料或小脚本的合理优势与维护代价。固定规则、当前状态或单步工具操作本身不构成新技能理由；没有独立缺口时可保留、简化或暂缓。合并/退场只是候选，先查引用、使用副本、兼容需求和授权，不能据此直接删除；判断方法见 [质量协议](skill-evaluation.md)。

创建或显著改变职责时用轻量 Skill Spec 设计 Goal、Scope、Trigger、Inputs、Outputs、Workflow、Resources、Constraints、Evaluation、Maintenance，见 [可选规格模板](../skills/af-skill-creator/templates/skill-spec.md)。它可以只存在于会话，不是必须长期维护的配置。局部修复只需记录缺陷、改动与验证，不强制全部阶段；只要方案时不写文件。

[af-skill-creator](../skills/af-skill-creator/SKILL.md) 支持创建、改进、审查、评估和维护，按意图选择分支，不规定所有技能采用其流程。它独立可用；产品方向和具体产品机制仍由两个产品技能各自负责。

1. 从真实任务或明确反馈确认要改善的行为，保留用户已有约束。重要改进按 [AF Skill Quality Loop](skill-evaluation.md) 记录根因、假设、副作用、失败条件，并在修改前冻结输入、技能快照与未经编辑的基线输出；缺基线不声称可靠前后改善。
2. 修改技能唯一编写源和必要资源；不同时编写项目或用户目录中的副本。
3. 核对引用、方法与示例是否一致，保留事实、推断和假设边界。示例若为合成，明确标记。
4. 运行 `python scripts/check_docs.py`；改动脚本或行为场景时另运行 `python -m unittest discover -s tests -v`，相关回归保留在 tests 并由 CI 执行。
5. 影响技能行为时选择有代表性的场景或真实任务验证，按统一协议分开记录结构、行为、对照和真实任务价值。保留原有能力回归、失败及无变化结果，未执行记 `not-run`；硬失败和关键退化不能被总分掩盖。结论注明范围，按证据保留、继续修改、回滚或待验证。
6. 同步技能目录、相关文档与 [验证记录](validation-report.md)。重要取舍记录到 decisions，不为每次措辞修改新增决策文件。

内容快照使用 Git 提交或本地冻结文件的散列定位。历史记录中的 0.1、0.2 等版本保留其原意；当前不需要 skill.json、plugin.json、发布渠道或包版本同步。

新增架构设计的组织示例见 [ADR 0008 与轻量规格](decisions/0008-architecture-design.md)：按六种任务模式加载决策、分解、质量与验证资源，使用架构专属量表和合成输入。它复用统一评估协议；架构模板和专业标准不进入通用检查器，也不要求其他技能采用相同输出。

## 轻量检查的范围

af-ui-design 的 [职责与轻量规格](decisions/0009-ui-design.md) 展示按三种 UI 模式组织的方法资源。项目继承与运行评审合并，减少重复；其 [专业量表](../skills/af-ui-design/evals/rubric.md) 区分方案质量、真实渲染和用户价值。截图 fixture、UI 状态与交互判据留在技能自身，不扩大通用检查器或其他技能的输出格式。

检查器仅使用标准库，核对入口必需字段、目录命名、常见行内 Markdown 文件链接和可选行为场景。代码块、行内代码和 HTML 注释不作为真实链接检查；支持链接标题、尖括号路径与转义/配对括号。它不是完整 CommonMark/YAML 解析器，不覆盖引用式链接、HTML 链接、复杂嵌套块容器或章节锚点，不访问外网，也不证明引用支持结论或技能实际被调用。

示例文件可以独立存在，不因文件名要求配套账本或报告。产品研究的 C 编号映射由 tests/test_product_intelligence.py 单独检查，不作为其他技能的格式要求。

evals/scenarios.json 是可选项，场景数量不固定；每项包含 id、request、shouldTrigger 和 expected，有原始输入时增加 inputFiles（相对 evals 目录，目标须在当前技能内）。执行者只接收请求、原始材料和适用技能，审查者随后读取 expected，不把期望答案预先交给执行者。定义完整和路径存在不等于行为已通过。

多轮行为场景可以使用 followup 与 followupExpected；后者仅供后续审查。通用检查器不验证这些技能专属观察的完整性或语义；统一评估协议约束证据与记录，不把技能专属输出或评分语义加入通用检查器。修订错误预期需保留旧新标准、依据和受影响结果，不能为通过率改答案。

技能文件夹应能完整复制使用；内部资源链接留在技能目录内，作者仓库的维护文档在 docs 单独链接技能。技能内评估说明可注明仓库根路径 `docs/skill-evaluation.md` 仅供 AgentForge 维护使用，不把外部文件设为执行依赖，也不复制整套仓库规范。当前结构示范见 [产品研究技能](../skills/af-product-intelligence/SKILL.md)。
